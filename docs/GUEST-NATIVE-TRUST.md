## Probe, setup controls, and receipts

`cmd/dibd/guest_native_probe_test.go` is an opt-in acceptance probe against the
actual binaries selected by `DIBS_NATIVE_CODEX` / `DIBS_NATIVE_CLAUDE`.
Without those variables it skips; a skip proves no native-client support.
The probe retains the original strict zero-path-length expectation. Its known
failure is evidence, not a passing gate. It has not been turned green by
loosening the CA, omitting the intermediate case, or changing the expectation.

It enters through `guestTLS` / `ensureGuestCA`, then a real TLS 1.3 loopback
listener with the production invitation-only `publicGate` and real MCP server.
Its credentials, encrypted ledger, CA/key, and config directories are temporary.
Codex uses only `initialize`, `initialized`, and `mcpServerStatus/list`, with no
thread ID. Claude uses only isolated `mcp add` and `mcp list`. The client process
receives `CODEX_CA_CERTIFICATE` or `NODE_EXTRA_CA_CERTS`; no user/system store is
changed. Go pre-verification asserts every selected fixture's intended validity
before the native connection, and the fixture counts HTTP requests after TLS.

Permissive roots and roots with individual constraints removed are **diagnostic
controls only**. They are never generated by the production path or offered to
guests. Codex's automatic marketplace sync initially caused two temporary-dir
cleanup failures after process exit. The corrected fixture sets `plugins=false`
in its isolated Codex configuration, leaving MCP/TLS verification unchanged.
Those earlier cleanup failures are retained, not attributed to TLS.

## Observations and their boundaries

Codex 0.159.2 accepts the production root and intended IPv6 leaf, returning 50
MCP tools after two HTTP requests. Unknown root, expired leaf, wrong IP, mixed
intended/out-of-range IPv6 or IPv4, DNS-only, mixed IP/DNS, and reserved-DNS
leaves are refused with zero HTTP requests. In particular, `invalid` and
`anything.invalid` are not an acceptable all-DNS-exclusion replacement.

Codex accepts an intended-IP leaf through an intermediate signed by the root
despite its `pathLen=0`. It nevertheless rejects, separately, intermediate
chains containing DNS-only leaves, intended plus out-of-range IPv6 SANs, and
intended IPv6 plus unrelated DNS SANs, with zero HTTP requests. Thus the measured
name restrictions survive a chain, while the root path-length property does not.
Do not call the original strict probe green or claim native enforcement of that
property. Architect message 15360 proposes treating name scope as the support
boundary and path length as defence in depth; that is an explicit acceptance
decision to review, not a certificate modification made by this probe.

This distinction is consistent with the trust-anchor treatment described in
[RFC 5280 section 6.1](https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1):
a self-signed trust-anchor certificate is outside the prospective certification
path, and applications may add further restrictions. The RFC alone proves
neither Codex's actual name-constraint enforcement nor safe guest support; the
native measurements above are the evidence for those specific claims.

The native probe does **not** prove exclusive trust in the guest CA, and does
not prove that native TLS enforces the printed SPKI pin. The examined Codex
source's custom-CA policy adds supplied certificates to its normal roots;
source is not a runtime measurement of this installed binary. A successful
extra-CA connection is narrower than an endpoint-scoped, guest-root-only
transport. The original real-listener Go client uses only its selected root,
but that property must not be borrowed to describe the native harness. A
native recipe's precise trust promise still needs an explicit decision.

Claude Desktop 2.1.284 accepts permissive DNS, IPv4, and IPv6 controls, so the
extra CA and actual MCP route work. It also accepts an empty-DNS-exclusion-only
root with an IPv4 leaf, and an IPv6-constrained root with a DNS leaf (the latter
has no DNS restriction). An IPv6-constrained root with its intended IPv6 SAN,
both with and without the empty DNS exclusion, fails before any HTTP request:
`UNSUPPORTED_CONSTRAINT_TYPE: unsupported name constraint type`.
Therefore the discriminating failure is evaluating IP name constraints against
an IP SAN, not parsing empty dNSName alone. The production guest root is safe
but unusable in this measured build. It is unsupported; no CA is weakened to
suit it. Its negative cases are not independent proof of expiry/path-length
enforcement, since the constraint failure already prevents positive use.

PATH Claude 2.1.233 additionally rejects its permissive literal-IPv6 control with
`ERR_TLS_CERT_ALTNAME_INVALID`; DNS/IPv4 controls work. That version must not be
confused with Desktop 2.1.284, whose IPv6 control works.

## Options for the operator, not implemented alternatives

1. **Keep the production constrained CA, measure the actual cloud runtime.**
   No authority is broadened. Unsupported runtimes remain unusable, and passing
   local TLS says nothing about external IPv6 reachability. The cloud probe must
   perform both a positive connection and the malicious-name/chain matrix.
2. **A Dibs-owned, endpoint-scoped stdio adapter, behind a separate design.**
   A Go transport could validate the exact guest root/SPKI, intended address,
   chain, and redirect policy without adding a CA to the harness's general HTTP
   transport. Residual costs are another client process, lifecycle/backpressure
   and protocol/task/identity compatibility work; none of that exists here yet.
   This would be a transport adapter, not permission to host or resume an agent.
3. **A native endpoint-pin feature, if a future runtime actually provides one.**
   Requires measurement through that feature, not a PEM/pin merely printed in a
   recipe. No native per-server pin feature was proved in this work.
4. **DNS-excluded-only CA, with no IP constraint: broader authority, not a fix.**
   Its signing key can issue trusted certificates for any IPv4/IPv6 endpoint.
   A malicious holder able to intercept/route traffic could impersonate another
   IP-addressed HTTPS service, including another Dibs board. Because the extra
   CA setting affects the whole harness process, exposure is not limited to the
   configured MCP endpoint. This is a material change in the trust boundary,
   requires an operator decision, and is neither shipped nor offered.

Disabling TLS checks, importing the guest CA into system roots, or silently
using a reserved DNS name are not options. No option removes the need for
separate-network WAN proof, or for re-invitation when the address/pin changes.
